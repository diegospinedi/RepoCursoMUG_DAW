# Decisiones FEAT-005: Integración continua para los pull requests

| ID | Decisión | Motivo | Quién |
|---|---|---|---|
| D-01 | Las e2e corren en el mismo job que el resto, después de las pruebas de .NET y de la web | El usuario eligió "Sí, incluirlas" (no un job aparte). Un solo job reutiliza la compilación y las dependencias ya instaladas, y si falla algo antes no gasta minutos en navegadores | Usuario (CLASSIFY) |
| D-02 | Solo tres acciones, todas oficiales de `actions/`, fijadas por el SHA del commit de su versión con la versión en un comentario: `actions/checkout` v7.0.1 (`3d3c42e5aac5ba805825da76410c181273ba90b1`), `actions/setup-dotnet` v6.1.0 (`0f4a354dd5547a28c70b7853dbd95d5b67886e73`), `actions/setup-node` v7.1.0 (`949feb2413d6458794dcd2491c4babbbce0c15c1`) | Una etiqueta se puede mover; el SHA no. SHA leídos de la API de GitHub el 2026-11-07; en CODE se vuelven a verificar con `git ls-remote` contra la etiqueta. La lista cerrada también impide publicar artefactos (`upload-artifact`, `cache`) con bases o resultados de pruebas | Claude (PLAN), a partir de WARN 4 y WARN 6 del auditor |
| D-03 | Runner `ubuntu-24.04` fijo, no `ubuntu-latest` | Un cambio de imagen no cambia la corrida sin que nadie lo decida. Windows y macOS quedan fuera de alcance (PRD) | Claude (PLAN) |
| D-04 | .NET pasa a tener archivos de bloqueo de NuGet (`RestorePackagesWithLockFile` en `Directory.Build.props`, un `packages.lock.json` por proyecto) y la corrida de CI restaura en modo bloqueado (`RestoreLockedMode` cuando `CI` es `true`) | AC-02 pide que la verificación falle si las dependencias no coinciden con el archivo de bloqueo; sin bloqueo de NuGet las dependencias transitivas podían cambiar entre corridas. En la PC de desarrollo no hay modo bloqueado: un cambio de paquete actualiza el archivo y se commitea con él | Usuario (PLAN, WARN 14 del auditor) |
| D-05 | La regla `--host-resolver-rules` pasa a una constante que reciben los tres navegadores de Playwright (`chrome`, `msedge` y el diagnóstico `chromium`) | FR-10: la suite de punta a punta solo habla con `localhost` en cualquier navegador; el diagnóstico `chromium` tampoco queda afuera | Claude (PLAN), a partir del análisis de impacto |
| D-06 | En la corrida se usan los Chrome y Edge estables que trae la imagen `ubuntu-24.04`: se instalan solo sus dependencias de sistema (`npx playwright install-deps chrome msedge`), se imprimen sus versiones y se genera el certificado de desarrollo con `dotnet dev-certs https` | `npx playwright install chrome msedge` corta si el navegador ya está instalado y forzarlo baja una versión sin fijar; con la imagen fija la versión cambia solo cuando cambia la imagen, y queda en el registro de cada corrida. El certificado se genera en cada corrida y se descarta con el runner | Claude (PLAN), a partir de WARN 5 del auditor |
| D-07 | Las reglas del workflow, del bloqueo de NuGet y de los hosts de las pruebas viven en `e2e/ci.mjs` y `e2e/ci.test.mjs` y corren dentro de `npm run test:unidad` | El usuario lo eligió: `test:unidad` ya está declarado en `AGENTS.md` y la CI lo corre; sin dependencias nuevas (las reglas leen texto, sin parser de YAML). `e2e/README.md` dice que `test:unidad` también revisa la CI | Usuario (PLAN, WARN 13 del auditor) |
| D-08 | Node se instala con `node-version: 22` | `engines` de `web/` y `e2e/` pide `^22.22.2`; la última 22.x lo cumple y trae npm ≥ 10.9.8 | Claude (PLAN) |
| D-09 | 11 criterios de aceptación en un solo ticket (W-PRD-06) | Es un único workflow y cada criterio es uno de sus pasos | Usuario (DEFINE) |
| D-10 | Los comandos que la CI tiene que correr están en una lista fija (`COMANDOS_DEL_PROYECTO`, directorio y comando) y una prueba verifica que cada uno figura en la sección "Stack" de `AGENTS.md` | La sección "Stack" es prosa y no se puede partir en comandos sin adivinar; la lista con directorio además detecta un comando corrido en la carpeta equivocada | Claude (PLAN), a partir de WARN 11 del auditor y del análisis de impacto |
| D-11 | AC-07 se demuestra con una corrida en rojo provocada a propósito en el pull request (un commit temporal que rompe una prueba, revertido después) | Una corrida verde no prueba que una falla deje el pull request en rojo con el nombre del paso. El push se hace con la confirmación del usuario | Claude (PLAN), a partir de WARN 16 del auditor |
| D-12 | El SDK de .NET queda en `10.0.x` (la última 10.0 de la corrida), sin `global.json` | Fijar el SDK cambia también el entorno de desarrollo local y no lo pide el PRD; los paquetes sí quedan fijados (D-04) | Claude (PLAN) |
| D-14 | `NuGet_CadaProyectoConLockfile` lee los archivos con `git ls-files -z --cached --others --exclude-standard`, no solo `git ls-files` | Cuenta los archivos de bloqueo antes de commitearlos; en la CI el checkout trae solo lo commiteado y da lo mismo. `-z` evita que las rutas con tildes queden entre comillas | Claude (CODE, Block 1, supuesto del implementador revisado), 2026-11-07 |
| D-15 | `revisarPropsNuGet` exige que toda asignación de `RestorePackagesWithLockFile` y `RestoreLockedMode` valga `true` y esté fuera de `Target` y `Choose`; `RestoreLockedMode` siempre con la condición de CI (comillas simples o dobles) y al menos un `RestorePackagesWithLockFile` sin condición; un elemento vacío cuenta como distinto de `true`. Reglas `archivo-de-bloqueo` y `modo-bloqueado` | En MSBuild gana la última asignación, y un grupo dentro de `Target` o `Choose` no es global: sin esto la prueba aprobaba un props que no bloquea (WARN 1 y 2 del auditor, ronda 1). Los nombres de regla no los fija la spec | Claude (CODE, Block 1, rondas 1 y 2), 2026-11-07 |
| D-16 | Quedan como WARN del Block 1: nombres de propiedad con otras mayúsculas no se reconocen, solo se revisa `Directory.Build.props` (no `Import` ni `.csproj`), una condición de CI repetida en grupo y elemento se rechaza, y la prueba `NuGet_SinModoBloqueado_Rechazado` agrupa muchos casos | En la CI el modo bloqueado falla con NU1004 de todos modos; ningún `.csproj` cambia esas propiedades hoy. No justifican una tercera ronda | Claude (CODE, Block 1, auditor ronda 2), 2026-11-07 |
| D-17 | `revisarWorkflow` es más estricto que el texto de la spec en tres reglas: `permisos` rechaza `write`, `write-all` y `read-all` dentro de cualquier bloque `permissions:` (no busca `write` en todo el texto, que rechazaba nombres de paso); `secretos` rechaza la palabra `secrets` (también en comentarios) y `github['token']`; `instalacion` acepta opciones antes del subcomando y rechaza además `exec`, `x`, `update`, `up` y abreviaturas de `install`, y revisa los `run` planos de varias líneas. `comandos` no cuenta un paso con `if:` (cualquier valor) o `continue-on-error` distinto de `false` (en el paso o el job), y rechaza `defaults` con `working-directory`. `on:` en flujo de varias líneas se junta hasta el cierre | FAIL 1-3 y WARN 3-6 de la auditoría del Block 2, ronda 1: cada uno era una aprobación falsa de una regla de la spec o de FR-07. La spec no se toca en CODE; las 12 reglas conservan sus nombres | Claude (CODE, Block 2, ronda 2), 2026-11-07 |
| D-18 | Límites conocidos de `revisarWorkflow`, aceptados como WARN: no protege contra un pull request malicioso desde un fork (puede editar `ci.yml` y `e2e/ci.mjs`; la protección real es de GitHub: sin secretos y token de solo lectura); escapes `\x..` y claves `?` de YAML; formas no soportadas con mensaje engañoso; `pnpm`/`yarn`/`bunx`; continuación con `\` dentro de `run: \|`; `npm create`, `npm init`, `npm audit fix`; `npx --no-install --yes`; `if:` a nivel del job; `shell:` que cambia el intérprete; `env` con `CI: "false"`, que apaga el modo bloqueado de NuGet; líneas de más de 120 columnas en `ci.test.mjs` | Las reglas protegen contra errores de quienes mantienen el repo, no contra un atacante que controla el workflow del pull request. Cerrarlos todos exige un parser de YAML o una lista cerrada de comandos, que es otro diseño | Claude (CODE, Block 2, auditor ronda 2), 2026-11-07 |
| D-19 | Pendiente de decisión del usuario: configuración del repositorio en GitHub (aprobación para workflows de colaboradores externos, protección de `master` exigiendo la CI, `CODEOWNERS` sobre `.github/` y `e2e/ci*.mjs`) | Es la protección real frente a forks (D-18); es configuración externa al código y queda a criterio del usuario | Pendiente — usuario |
| D-20 | El job de la CI usa un `HOME` fuera del código (lazo correctivo CODE→PLAN para sumarlo a la spec). La línea "Content root path" de `Microsoft.Hosting.Lifetime`, que en `Production` puede llevar el nombre del usuario si la aplicación se instala dentro de su perfil, queda para un FIX aparte | La primera corrida del PR #11 falló en "Pruebas de .NET" (9 de 1415): en GitHub el código queda en `/home/runner/work/…`, dentro del perfil `/home/runner`, y las pruebas que verifican que los logs y errores no lleven la carpeta del usuario la encuentran en el log de arranque y en los stack traces Debug. Opción 1 de 3 (las otras: corregir el log en este ticket, o relajar las pruebas) | Usuario (CODE), 2026-11-07 |
| D-21 | `hostsExternos` es más estricto que el texto de la spec: las IPv4 privadas solo se aceptan en decimal, 0-255 y sin ceros iniciales (`010.0.0.1` es `8.0.0.1` para el parser de URL); el host es lo que sigue al último `@`; un carácter no ASCII es parte del host; `www.w3.org` solo con `/2000/svg`, `/1999/xhtml`, `/1999/xlink` y la DTD de SVG 1.1 (que `LogoMarca.cs` rechaza sin pedirla). `navegadoresFaltantes` reemplaza el caso tautológico "sin msedge". El descarte de comentarios XML de `revisarPropsNuGet` pasa a `quitarComentarios` (alerta de CodeQL js/incomplete-multi-character-sanitization en el PR #11) | FAIL 1-2 y WARN 3-6 de la auditoría del Block 3, ronda 1: cada uno era una aprobación falsa de "cualquier otra IP literal o nombre es externo". La spec no se toca en CODE | Claude (CODE, Block 3, ronda 2), 2026-11-07 |
| D-22 | Límites conocidos del Block 3, aceptados como WARN: `hostsExternos` solo reconoce `http`/`https` (no `ws`/`wss`; hoy no hay ninguna); un `<![CDATA[` con `<!--` adentro puede esconder una propiedad a `revisarPropsNuGet`; `quitarComentarios` tiene costo cuadrático con entradas anidadas a propósito; el README de `e2e/` no menciona los subdominios de `example.com` | Ninguno aparece en los archivos reales; todos requieren un archivo armado a propósito por quien mantiene el repo | Claude (CODE, Block 3, revisiones ronda 2), 2026-11-07 |
| D-23 | Límites conocidos de la regla `perfil` (Block 4), aceptados como WARN: escapes `\x..` en comillas dobles y escalares planos de varias líneas en el valor de `HOME`; `HOME` en el `env` de un paso que pisa al del job, o escrito en `$GITHUB_ENV`; `HOME: /tmp/` o `/tmp/.` (todo `/tmp`); ninguna regla controla que el paso "Crear la carpeta del perfil" exista y vaya antes del checkout (su comentario puede ser inexacto: `actions/checkout` escribiría su configuración temporal en `RUNNER_TEMP`). Va al FIX de D-20 junto con "Content root path" | Mismo criterio que D-18 y D-22: protegen contra errores de quien mantiene el repo, no contra un workflow armado a propósito; la corrida con el `ci.yml` real no los usa. La simulación completa con `HOME` nuevo y `CI=true` dio 1415/1415 | Claude (CODE, Block 4, revisiones), 2026-11-07 |

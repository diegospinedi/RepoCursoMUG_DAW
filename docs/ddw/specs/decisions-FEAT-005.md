# Decisiones FEAT-005: Integración continua para los pull requests

| ID | Decisión | Motivo | Quién |
|---|---|---|---|
| D-01 | Las e2e corren en el mismo job que el resto, después de las pruebas de .NET y de la web | El usuario eligió "Sí, incluirlas" (no un job aparte). Un solo job reutiliza la compilación y las dependencias ya instaladas, y si falla algo antes no gasta minutos en navegadores | Usuario (CLASSIFY) |
| D-02 | Solo tres acciones, todas oficiales de `actions/`, fijadas por el SHA del commit de su versión con la versión en un comentario: `actions/checkout` v7.0.1 (`3d3c42e5aac5ba805825da76410c181273ba90b1`), `actions/setup-dotnet` v6.1.0 (`0f4a354dd5547a28c70b7853dbd95d5b67886e73`), `actions/setup-node` v7.1.0 (`949feb2413d6458794dcd2491c4babbbce0c15c1`) | Una etiqueta se puede mover; el SHA no. SHA leídos de la API de GitHub el 2026-11-07; en CODE se vuelven a verificar con `git ls-remote` contra la etiqueta. La lista cerrada también impide publicar artefactos (`upload-artifact`, `cache`) con bases o resultados de pruebas | Claude (PLAN), a partir de WARN 4 y WARN 6 del auditor |
| D-03 | Runner `ubuntu-24.04` fijo, no `ubuntu-latest` | Un cambio de imagen no cambia la corrida sin que nadie lo decida. Windows y macOS quedan fuera de alcance (PRD) | Claude (PLAN) |
| D-04 | .NET pasa a tener archivos de bloqueo de NuGet (`RestorePackagesWithLockFile` en `Directory.Build.props`, un `packages.lock.json` por proyecto) y la corrida de CI restaura en modo bloqueado (`RestoreLockedMode` cuando `CI` es `true`) | AC-02 pide que la verificación falle si las dependencias no coinciden con el archivo de bloqueo; sin bloqueo de NuGet las dependencias transitivas podían cambiar entre corridas. En la PC de desarrollo no hay modo bloqueado: un cambio de paquete actualiza el archivo y se commitea con él | Usuario (PLAN, WARN 14 del auditor) |
| D-05 | La regla `--host-resolver-rules` pasa a una constante que reciben los tres navegadores de Playwright (`chrome`, `msedge` y el diagnóstico `chromium`) | FR-10: la suite de punta a punta solo habla con `localhost` en cualquier navegador; el diagnóstico `chromium` tampoco queda afuera | Claude (PLAN), a partir del análisis de impacto |
| D-06 | En la corrida se usan los Chrome y Edge estables que trae la imagen `ubuntu-24.04`: se instalan solo sus dependencias de sistema (`npx playwright install-deps chrome msedge`), se imprimen sus versiones y se genera el certificado de desarrollo con `dotnet dev-certs https` | `npx playwright install chrome msedge` corta si el navegador ya está instalado y forzarlo baja una versión sin fijar; con la imagen fija la versión cambia solo cuando cambia la imagen, y queda en el registro de cada corrida. El certificado se genera en cada corrida y se descarta con el runner | Claude (PLAN), a partir de WARN 5 del auditor |
| D-07 | Las reglas del workflow, del bloqueo de NuGet y de los hosts de las pruebas viven en `e2e/ci.mjs` y `e2e/ci.test.mjs` y corren dentro de `npm run test:unidad` | El usuario lo eligió: `test:unidad` ya está declarado en `AGENTS.md` y la CI lo corre; sin dependencias nuevas (las reglas leen texto, sin parser de YAML). `e2e/README.md` dice que `test:unidad` también revisa la CI | Usuario (PLAN, WARN 13 del auditor) |
| D-08 | Node se instala con `node-version: 22` | `engines` de `web/` y `e2e/` pide `^22.22.2`; la última 22.x lo cumple y trae npm ≥ 10.9.8 | Claude (PLAN) |
| D-09 | 11 criterios de aceptación en un solo ticket (W-PRD-06) | Es un único workflow y cada criterio es uno de sus pasos | Usuario (DEFINE) |
| D-10 | Los comandos que la CI tiene que correr están en una lista fija (`COMANDOS_DEL_PROYECTO`, directorio y comando) y una prueba verifica que cada uno figura en la sección "Stack" de `AGENTS.md` | La sección "Stack" es prosa y no se puede partir en comandos sin adivinar; la lista con directorio además detecta un comando corrido en la carpeta equivocada | Claude (PLAN), a partir de WARN 11 del auditor y del análisis de impacto |
| D-11 | AC-07 se demuestra con una corrida en rojo provocada a propósito en el pull request (un commit temporal que rompe una prueba, revertido después) | Una corrida verde no prueba que una falla deje el pull request en rojo con el nombre del paso. El push se hace con la confirmación del usuario | Claude (PLAN), a partir de WARN 16 del auditor |
| D-12 | El SDK de .NET queda en `10.0.x` (la última 10.0 de la corrida), sin `global.json` | Fijar el SDK cambia también el entorno de desarrollo local y no lo pide el PRD; los paquetes sí quedan fijados (D-04) | Claude (PLAN) |
| D-13 | Ajustes de la ronda 2 de la auditoría: `pull_request` como único evento, `npx --no-install`, importación de la configuración de Playwright con URL distintas por variante y control de los prefijos de navegador, IPv6 `[::1]` como local, verificación de los SHA con `git ls-remote` como criterio de cierre del Block 2 | Cada uno cerraba un falso aprobado posible en una regla de seguridad o de alcance (WARN N-1 a N-7 de la ronda 2) | Claude (PLAN) |

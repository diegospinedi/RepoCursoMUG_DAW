# Decisiones de FEAT-001c: Configuración de parámetros de negocio

| ID | Fecha | Fase | Decisión | Quién | Origen |
|---|---|---|---|---|---|
| D-01 | 2026-11-04 | PLAN | El múltiplo de redondeo comercial y el tope de identificación admiten hasta 2 decimales, como los importes de PRD-001 RF-19. El mínimo se valida antes que la escala: 0,001 muestra "El valor mínimo es 0,01." (AC-04) y 0,015 o 50,005 muestran "Ingresá hasta 2 decimales." | Usuario | arch-auditor WARN 6; el PRD no fijaba la escala |
| D-02 | 2026-11-04 | PLAN | Si el tope de identificación se graba vacío, queda sin valor y sigue el aviso de FR-08; también se puede vaciar un tope ya cargado. | Usuario | Derivado de AC-02 y FR-08; confirmado por el usuario |
| D-03 | 2026-11-04 | PLAN | Grabar reemplaza los cuatro valores juntos y la última grabación gana (una sola operadora, una PC); después de grabar, la pantalla vuelve a leer y muestra lo guardado. | Agente | arch-auditor WARN 9; R-08 del threat model |
| D-04 | 2026-11-04 | PLAN | Sin la fila de configuración (base alterada a mano) es un estado corrupto: la lectura lanza y la Api responde 500 genérico; no se recrea en silencio. | Agente | arch-auditor WARN 9; impact-scanner nota 4 |
| D-05 | 2026-11-04 | PLAN | Las pruebas e2e de configuración corren contra su propia Api y su propia base por navegador, separadas de las de acceso, que dejan la base con otra contraseña y bloqueada. | Agente | impact-scanner gap 4 |
| D-06 | 2026-11-04 | PLAN | No se registra quién cambió un parámetro: la contraseña es compartida por diseño (PRD-001). Cada grabación queda en el log de la Api con valores anteriores y nuevos y fecha y hora (R-04). | Agente | arch-auditor WARN 16 |
| D-07 | 2026-11-04 | PLAN | La traducción entre `CondicionFiscal` y su texto (`responsable_inscripto`, `monotributo`) vive en la política de dominio: el mismo texto es el contrato de la Api y el valor de la columna, y así hay una sola fuente. | Agente | arch-auditor ronda 2, N5 |
| D-08 | 2026-11-04 | CODE (Block 3) | Las tres infracciones de escala muestran "Ingresá hasta 2 decimales." en su campo, y las dos de rango del tipo (múltiplo y tope) "Ingresá un valor menor."; el registro de cada grabación (R-04) se escribe solo después de confirmar, con marcadores estructurados para los cuatro valores anteriores y nuevos y la fecha y hora UTC. | Agente (supuesto del implementador, aceptado por module-verifier y arch-auditor) | Block 3 |
| D-09 | 2026-11-04 | CODE (Block 5) | La pantalla acepta coma o punto como separador decimal, como dice la spec; no hay separador de miles. Riesgo conocido y aceptado: un tope escrito "350.000" se graba como 350. | Usuario | Supuesto 4 del implementador de Block 5; opciones ofrecidas: solo coma, punto de miles, dejarlo |
| D-10 | 2026-11-04 | CODE (Block 5) | Textos y comportamiento de la pantalla que la spec no fijaba: título "Configuración", botón "Grabar", 413 con "Los valores enviados son demasiado largos. Revisalos y grabá de nuevo." en `alicuotaIva`; si el GET inicial falla se muestra el mensaje general sin formulario; un campo desconocido en `errors` va como mensaje general; "La configuración se grabó." se borra al volver a grabar; enlace "Volver al inicio". | Agente (supuestos del implementador, a revisar por module-verifier y arch-auditor) | Block 5 |
| D-11 | 2026-11-04 | CODE (Block 5) | La spec se contradecía sobre el 413 en la pantalla ("Files": `campo413` `alicuotaIva`; "Error handling": mensaje general). Se resolvió a favor de "Error handling": un 413 al grabar se muestra como mensaje general con `role="alert"` ("Los valores enviados son demasiado largos. Revisalos y grabá de nuevo.") y se conservan los valores; `grabarConfiguracion` no usa `campo413`. Reemplaza la parte del 413 de D-10. En la práctica la pantalla no puede producirlo (cuatro campos de hasta 32 caracteres contra 1024 bytes). | Agente (orquestador), a partir de WARN 1 de module-verifier | Block 5 |
